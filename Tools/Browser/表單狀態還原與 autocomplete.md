# 瀏覽器的表單狀態還原（Form State Restoration）與 autocomplete

重新整理、回上一頁、複製分頁、關掉瀏覽器再回復 session 時，
瀏覽器會把使用者先前輸入的值**自動填回表單控制項**。

這是一個獨立於「密碼／地址自動填入」的機制，
它的配對規則寫得很簡單，也因此很容易踩到——
**配對錯了不會有任何錯誤訊息，值就是靜靜地跑到別的欄位去。**

---

## 還原的配對規則：key = (name, type)

瀏覽器不是靠 `id` 認欄位的，是靠 **`name` + `type`** 這一組 key：

1. 離開頁面時，把頁面上每個控制項的值存起來，
   以 `(name, type)` 分組，同一組內**依文件順序**排成一個清單。
2. 還原時，用同一把 key 找出當下頁面上的控制項，
   再把清單裡的值**依序（by index）**填回去。

也就是說，同一組裡的配對**純粹靠位置**，不看 `id`、不看 class、不看 DOM 路徑。

三個直接的推論：

| 推論 | 意思 |
|---|---|
| `name` 不同 → 各自成一組 | 一組一個成員，位置永遠對，還原一定正確 |
| `name` 相同 → 同一組 | 靠 index 配對，**組成員一變就整組位移** |
| **沒寫 `name`** ≠ 不會被還原 | 空字串也是一種「相同的 name」，全部擠在同一組 |

最後一項是最容易誤會的地方：不寫 `name` 不是「退出這個機制」，
而是「所有沒寫 `name` 的同型別控制項全部歸成同一組」，
是所有寫法裡**最容易位移**的一種。

`type` 也在 key 裡，所以 `type=date` 與 `type=text` 即使同名也不會互相干擾。

### 值型別不合會被吃掉

`type=date` 只接受 `yyyy-MM-dd`。位移之後如果拿到的是別的欄位的內容
（例如一段關鍵字），`input.value` 的 setter 會直接判定為無效值而變成**空字串**，
於是症狀看起來是「日期欄位莫名其妙變空的」，而不是「填錯值」。

## 什麼時候會觸發還原

表單狀態是存在 **session history entry** 上的，不是存在網址、cookie 或 localStorage。
所以判斷依據只有一條：

> **同一個 history entry 被重新呈現 → 會還原；產生新的 entry → 不會。**

### 會觸發（同一個 entry 被重新呈現）

| 情境 | 說明 |
|---|---|
| **重新整理**（F5 / Ctrl+R / 重新整理鈕） | 最常見的一條；entry 沒變，值原封不動填回來 |
| **回上一頁／下一頁** | bfcache 命中時整頁狀態直接復活；沒命中則重新載入後從 entry 取值重填 |
| **複製分頁**（Duplicate tab） | 連同整份 session history（含表單狀態）複製一份，所以新分頁一開就帶著舊值 |
| **Ctrl+Shift+T 復原剛關掉的分頁** | 同上，entry 被救回來 |
| **瀏覽器重開後回復上次的分頁** | 「繼續瀏覽上次開啟的網頁」、當機後回復，都走 session restore |
| **分頁被丟棄後重新載入** | Memory Saver／tab discard 把背景分頁釋放掉，回去看時重新載入同一個 entry |
| **系統睡眠／休眠／更新重開機之後** | 同上——**睡眠本身不會重新載入頁面**，會看到還原是因為期間分頁被丟棄或整個瀏覽器被重啟 |

### 不會觸發（產生新的 entry）

| 情境 |
|---|
| 在網址列輸入網址按 Enter |
| 點連結（即使連到同一頁） |
| 表單送出（GET／POST）後抵達的頁面 |
| `location.href = …`、`location.assign()`、`location.replace()` |
| 另開新分頁重新打開同一個網址 |
| 無痕／InPrivate 視窗關閉之後（整批 entry 都不留） |

### 兩個沒有獨立實測、但機制上可以推得的

- **`window.location.reload()`**：它是同一個 entry 的 reload，機制上屬於「會觸發」。
  先前遇到「條件消失」的案例不是這個機制失效，而是那些值**根本沒進到表單控制項**
  （由 JS 產生或只存在於網址上），所以沒有東西可還原。
- **Ctrl+Shift+R（清快取重新載入）**：仍是同一個 entry，但各家瀏覽器對表單值的處理不一致，
  要靠它「清掉欄位」並不可靠。

> 上表是依「同一個 entry」這條規則分類的，不是每一列都各自跑過實驗；
> 真正逐項量過的是下一節那兩組。

## 實測

### 情境一：同名 `name="qryDate"` 的兩個 date input

兩組都是同一個 `name`，差別只在**存檔時同組的成員數量是否穩定**：

| 情境 | 存檔時同組成員 | 還原後 |
|---|---|---|
| A）前面被動態插入 2 個 | 4 個 | `begin=[]`　`end=[]` ❌ |
| B）成員數量穩定 | 2 個 | `begin=[2026-01-01]`　`end=[2026-12-31]` ✅ |

行為與「`name` 是空字串」的情境**完全一致**——
非空但重複的 `name` 走的是同一條路徑。

> **重複的 `name` 不會保護你，唯一的 `name` 才會。**
> 把四個 date input 都改成 `name="qryDate"`，等於沒改。

### 情境二：`autocomplete="off"` 的效果

| 欄位 | 還原後 |
|---|---|
| `type=date` 無 `autocomplete` | `[]` ← 被位移成空字串（bug 重現） |
| `type=date` `autocomplete="off"` | `[2024-01-01]` ← 完全沒被還原，停在 HTML 預設值 |
| `type=text` 無 `autocomplete` | `[使用者輸入]` ← 正常還原 |
| `type=text` `autocomplete="off"` | `[預設文字]` ← 完全沒被還原 |

`autocomplete="off"` 確實關掉了這個還原機制，且**不需要有 `<form>`**（見下一節）。

規格依據是 HTML 標準的 autofill 章節：`autocomplete="off"` 的語意是
**「使用者代理不應記住這個控制項的值」**，涵蓋的正是重新載入／回上一頁時的還原。
它不是 Chromium 的怪癖，是有規範背書的開關。

## `autocomplete` 可以下在哪裡

不是只能下在 `<form>` 上，**可以直接下在個別欄位**，
而且該欄位不需要被任何 `<form>` 包住：

```html
<!-- 完全不在任何 form 裡，一樣生效 -->
<input type="date" id="acOff" value="2024-01-01" autocomplete="off">
```

| 放哪 | 效果 |
|---|---|
| `<input>` / `<select>` / `<textarea>` | 只管這一個控制項 |
| `<form autocomplete="off">` | 設定該表單**所有**控制項的預設值 |

**欄位自己的設定蓋過表單的**，所以可以做局部例外：

```html
<form autocomplete="off">
    <input name="a">                      <!-- 繼承 form → off -->
    <input name="b" autocomplete="on">    <!-- 自己覆寫 → on  -->
</form>
```

任何一層都沒寫時，預設是 `on`。

## 兩種解法解的不是同一件事

```
name 唯一          → 還原機制照常運作，只是配對正確  →「回上一頁，剛才查的條件還在」
autocomplete=off   → 直接關掉還原                    →「回上一頁，永遠回到 HTML 預設值」
```

| 解法 | 適合什麼欄位 |
|---|---|
| **`name` 唯一** | 使用者會希望「回上一頁條件還在」的查詢欄位——日期區間、關鍵字、人員 |
| **`autocomplete="off"`** | 明確不希望被記住的欄位——每次都要從預設值開始，或內容敏感、不該留在 history entry |

查詢條件通常屬於前者：`name` 唯一之後還原會正常帶回使用者上次查的區間，只是不再錯位；
改用 `autocomplete="off"` 則會讓欄位固定回到 HTML 上的預設值，
使用者複製分頁後就得重設條件——能解 bug，但體驗變差。

**修 bug 的是 `name` 唯一，`autocomplete="off"` 是產品行為的選擇。**

---

## 幾個容易搞混的邊界

- **它擋不了 `window.location.reload()` 造成的條件消失。**
  那是「根本沒有東西可還原」，跟這個機制無關——見〈什麼時候會觸發還原〉最後一節。
- **Chrome 對「密碼／地址自動填入」會刻意忽略 `autocomplete="off"`**，
  但本文講的 session 還原有確實遵守。兩者是不同的功能，不要用其中一個的行為去推論另一個。
- **`id` 在這裡完全沒有作用。** 只有 `name` 與 `type` 進 key。
- **動態插入欄位是引信。** 同名分組平常看起來都好好的，
  一旦有程式在某些情境下多插／少插了同組的成員，整組就開始位移。

## 檢查清單

- [ ] 頁面上所有 `input` / `select` / `textarea` 都有 `name`
- [ ] 這些 `name` 在同一頁內**唯一**（尤其是動態產生的那些）
- [ ] 不希望被記住的欄位，逐個加上 `autocomplete="off"`
